## Problem Statement

`ticket_prio_class/notebooks/2.0-classificacao-prioridade.ipynb` already has a working
priority classifier (Random Forest, grouped CV macro-F1 0.875±0.029, held-out test
macro-F1 0.910). The notebook's own "Próximos passos" section flagged an unresolved
question: `security_incident_flag`, `data_loss_flag`, and `payment_impact_flag` are the
tickets with the strongest raw signal in the EDA (max deviation up to 45.6pp), but they
occur in only 0.3%–1.6% of tickets and don't dominate the model's aggregate feature
importance (which is led by the more frequent `downtime_min`, `customers_affected`,
`error_rate_pct`). Aggregate macro-F1 gives no visibility into whether the model actually
catches these specific, highest-stakes tickets. That's the open question this increment
answers.

## What Makes This Cool

Most "I built a classifier" writeups stop at the aggregate score. Going one level deeper —
checking whether the model's blind spot is exactly the tickets that matter most
operationally — is the difference between a metric and a real triage story. It's also the
kind of thing that reads as engineering judgment, not just modeling mechanics, in a
mentor conversation.

## Preliminary Finding (from /plan-eng-review outside-voice pass)

Verified directly against the fitted pipeline and `test.csv` before this design was
finalized — this reframes Success Criteria and Next Steps below, so it's recorded here
rather than left implicit:

- **The effect is large, not marginal.** Rare-flag slice `high` recall is **0.626**
  against an aggregate baseline of 0.847 — a 22pp gap, about 3x the "5-10pp = weak" band
  originally proposed. Per flag: `security_incident_flag` 0.481 (N=36),
  `data_loss_flag` 0.64 (N=42), `payment_impact_flag` 0.643 (N=215). All three are
  unambiguously bad from a plain sliced `classification_report` — no confidence interval
  needed to see it.
- **The rare-flag slice is really ~4 companies, not 203-290 independent tickets.** The
  combined slice's 203 `high` tickets break down as {100002: 155, 100010: 40, 100020: 7,
  100008: 1} — **76.4% from a single company.** A Wilson interval (or any interval
  assuming i.i.d. Bernoulli trials) on this slice would overstate precision, because it's
  the *exact* company-clustering risk the notebook already treats as central everywhere
  else (sections 1, 2, and 5 — that's why grouped CV exists at all). This directly
  contradicts the original Success Criteria's Wilson-interval plan; superseded below by a
  per-company breakdown instead.
- **`class_weight="balanced"` is already active on all three candidate models**
  (confirmed in the notebook's model-candidates cell), so "try a class-weight adjustment"
  as a next fix must mean hand-tuned per-class weights beyond `"balanced"` — not
  re-verifying a setting that's already on.
- **`statsmodels` is not a project dependency** (absent from `pyproject.toml`, not
  installed in `.venv`) — moot now that the interval approach is dropped in favor of the
  per-company breakdown, which needs nothing beyond what's already imported.

## Approaches Considered

### Approach A: Promote pipeline first
Extract the notebook's winning `ColumnTransformer` + `RandomForestClassifier` into
`ticket_prio_class/modeling/train.py` + `predict.py`, following the Typer `app()` pattern
already used by `dataset.py`, with `joblib` model persistence. Fast (S effort, low risk),
directly closes "próximos passos" item 4, but promotes the model before checking its known
rare-class blind spot. Rejected for this increment — sequencing risk: might promote a
pipeline that needs revisiting once the audit below runs anyway.

### Approach B: Rare-class audit first (chosen)
Effort: S–M | Risk: Low
Add a focused check to the notebook: slice `X_test`/`y_test` down to tickets where
`security_incident_flag == 1` OR `data_loss_flag == 1` OR `payment_impact_flag == 1`, and
report recall/precision/confusion specifically on that slice — both combined and broken
out per individual flag — separate from the aggregate `classification_report`. If recall
on `high` within that slice is weak — confirmed: it is, see Preliminary Finding above —
a *hand-tuned* class-weight adjustment beyond the already-active `"balanced"` setting
(cheap, stays inside this analysis) is the candidate fix to try within this increment if
there's time; if that's not enough, escalate to the `predict_proba` threshold route as a
separate follow-up — that one is really Approach C's territory (see Open Questions), not
a same-size fix. Any fix attempt is validated via the grouped CV (`StratifiedGroupKFold`,
same as the existing CV cell), never by re-touching `test.csv` — the notebook is explicit
that the test set is touched exactly once, and a second touch to iterate on a fix is
exactly the test-set peeking that discipline exists to prevent. Either way, this
increment's required deliverable is the audit + verdict + decision below (Next Steps
1-4), not the fix itself — a fix attempt is a bonus, not a requirement.

### Approach C: Reframe as cost-sensitive triage
Use `predict_proba` plus a justified probability threshold or cost matrix that
maximizes recall on `high` within an acceptable false-positive budget, then promote that
adjusted decision rule (not raw `.predict()`) into `train.py`/`predict.py`. Ties directly
to the impact-vs-urgency framing from ticket-priority research (aggregate macro-F1 hides
which mistakes are actually expensive). Bigger lift (M effort, medium risk — the threshold
choice needs defending) and duplicates work Approach B would surface anyway. Deferred:
worth doing only if the Approach B audit finds a real gap to fix this way.

## Recommended Approach

**Approach B — rare-class audit first.** Cheapest of the three, directly closes the exact
gap the user's own notebook already flagged as "próximos passos" item 1, and produces the
sharpest single artifact for a mentor conversation: not "here's my score" but "here's
whether my model catches the tickets that actually matter." The Preliminary Finding above
already confirms the gap is real and large (22pp) — so Approach C (cost-sensitive
reframe) is now a live candidate for the *following* increment, not just a hypothetical
one; Approach A (promote as-is) is off the table until a fix is attempted or explicitly
deferred, since promoting a pipeline with a confirmed 22pp blind spot on its highest-stakes
tickets without saying so would misrepresent the model.

## Open Questions

- Given the rare-class slice recall is confirmed weak (0.626 vs. 0.847 baseline), is a
  hand-tuned class-weight adjustment (beyond the already-active `"balanced"` — e.g.
  explicitly overweighting `high`, cheap, stays within the current Random Forest) or a
  `predict_proba` threshold tweak the better fix to try first? Note the threshold route
  is more involved than it sounds for a 3-class model — there's no single scalar cutoff;
  it means a custom decision rule that overrides argmax (e.g., "predict `high` if
  P(high) > t, else argmax over the rest"), closer in effort to Approach C than to a
  quick class-weight change. Either way, validate via grouped CV, not a second
  `test.csv` touch.
- Should the audit also look at pooled CV predictions, given how few rare-flag tickets
  exist overall? The existing CV step (`cross_val_score`) doesn't retain per-sample
  predictions — this would mean re-running CV with `cross_val_predict` instead, using the
  exact same `StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=RANDOM_STATE)`
  and `groups=train_feat["company_id"]` so the fold structure doesn't silently change.
  Worth doing if the `test.csv` slice reads too small to trust on its own — but note the
  splitter stratifies on `priority`, not on the rare flags, so per-fold coverage of
  rare-flagged `high` tickets could still be uneven (possibly zero in some folds); pooling
  across all 5 folds raises the total N, but read individual folds with caution.

## Success Criteria

- A new notebook cell (or two) in `2.0-classificacao-prioridade.ipynb` that isolates
  the `security_incident_flag`/`data_loss_flag`/`payment_impact_flag` slice — combined
  and per individual flag, reporting each flag's own N since the three flags can overlap
  on the same ticket — and reports precision/recall/confusion for it specifically,
  separate from the aggregate report.
- A fixed reference point for the verdict: recall on `high` within the rare-flag slice,
  compared directly against recall on `high` in the aggregate `classification_report`
  (0.847 on `test.csv` today). Call it "weak" if it lands more than ~5-10pp below that
  baseline — a rough band, not a number picked after the fact, and one that accounts for
  how wide the plausible range is at this sample size.
- An explicit note that the rare-flag slice is small (test.csv: 290 rows in the combined
  slice, 203 of them `high`) and that the per-flag slices will be smaller still, given
  individual flag rates of 0.3%–1.6% — report each flag's own N alongside its numbers, and
  read all of it with the same caution the notebook already applied to `val.csv`'s 44
  `high` tickets, not as a precise estimate.
- A per-company breakdown of the combined slice's `high` recall — not a Wilson interval.
  Confirmed: the slice is dominated by a handful of companies (76.4% of its `high`
  tickets from one company), so an interval assuming independent trials would understate
  the real uncertainty. A per-company table (recall on `high`, N per company) surfaces
  that clustering directly, costs no new dependency, and matches the notebook's existing
  company-grouped mindset — more honest than a misapplied CI, not less rigorous.
- A one-paragraph written verdict: does the current Random Forest catch these tickets
  well enough, or not — with the number to back it up either way.
- A clear, one-line decision on what happens next (promote as-is / fix then promote /
  reframe as cost-sensitive) based on what the audit finds.

## Implementation Verdict (from execution)

The notebook cells were written and run end-to-end (`jupyter nbconvert --execute`,
zero errors). Real output, matching the Preliminary Finding above exactly:

- Combined rare-flag slice (N=290): recall(high) = 0.626 vs. 0.847 aggregate — 22pp gap,
  "weak" by 3x the design's own threshold.
- Per-flag: `security_incident_flag` 0.481 (N=36), `data_loss_flag` 0.640 (N=42),
  `payment_impact_flag` 0.643 (N=215).
- **New finding from the per-company breakdown, not anticipated by the design doc:**
  precision(high) = **1.000 in every single slice** (combined and all 3 flags) — every
  "high" prediction the model makes on rare-flag tickets is correct. The gap is 100%
  a recall problem: the model isn't predicting `high` often enough on these tickets,
  not predicting it wrongly. And it's concentrated by company — the largest company
  (100002) holds recall around 0.59-0.66 across every slice, while smaller companies
  (100020, 100008) sit at 0.0-0.33, with 100008 hitting 0 recall on 1 (combined),
  1 (security), and 0 (data_loss/payment — N_high=0 there) `high` tickets.
- **Perfect precision + moderate recall is a decision-threshold signature, not a
  class-weight signature.** `class_weight="balanced"` is already active and yields this
  exact pattern — the model is conservative about predicting `high`, correctly so when
  it does, but not often enough for rare-flag tickets outside the most-represented
  company. Escalating to **Approach C** (a `predict_proba` threshold/cost-matrix
  override, not raw `.predict()`) is the better-supported next move over a further
  class-weight tweak, which would likely just trade away the current perfect precision
  rather than target the real gap. Any threshold chosen must be validated via the
  grouped CV, never a second `test.csv` touch (per the guardrail above).
